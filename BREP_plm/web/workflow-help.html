Build a workflow

A workflow describes a process as steps connected by paths. Forms collect information, reviews request decisions, and automated steps check or update a part. The flowchart runs from top to bottom: ovals start or end a process, rectangles perform work, parallelograms collect input, and diamonds choose a path. Administrators design workflows; assigned participants complete tasks in their Inbox.

Your first workflow

  1. Create a workflow and choose a template. Smart form starts with Start → Complete request → Complete. Choose the template before customizing: changing it replaces the current draft.
  2. Give it a descriptive name and describe when people should use it.
  3. Click a step to edit its details. For a form, set its assignees; initiator assigns the person who starts the process.
  4. Click a palette button to add a step, or drag it to a position on the canvas. Drag existing steps to arrange them.
  5. Drag a step’s bottom OUT connector to another step’s top IN connector (or its box) and release to create a path. You can also click OUT, then IN, or choose From step and To step in the Paths section and click Add path. Set its outcome in the Paths section.
  6. Add the information you need in Form fields. The starter includes a Reason field required at the start.
  7. Save the workflow. Open Workflows and start a process to try it. Complete assigned tasks in the Inbox and follow progress in the process monitor.

Example: Start → Request details (Form) → Approve request (Review) → Complete (End). Connect the review to Complete with success, and add another End step named Rejected with a reject path.

Workflow settings

  • Available to start: makes the workflow available for new processes. Save changes to apply them.
  • Allowed part types: leave the selection empty for all types. Hold Ctrl (Windows/Linux) or Command (Mac) to select or deselect individual types.
  • Who can start: comma-separated user:username, group:name, or * for everyone. Empty allows authors. Administrators can also start workflows.
  • Require this workflow for part release: This enables the workflow requirement for applicable part types; add a Status step to perform the lifecycle change.

Step types

StepUse it for
StartThe single entry point. Every workflow needs exactly one.
FormA task for assigned people to enter information and complete or reject. One assigned participant completes the task.
Human decisionA diamond with at least two named outgoing paths. An assigned person chooses one path; the first response completes the decision.
Programmatic decisionA diamond that calls step(input). Return { outcome: "yes" } (or another outgoing path name) to choose exactly one route. An unknown outcome blocks the process for correction.
ReviewAssigned reviewers approve or reject independently. Required approvals of 0 means all assigned reviewers. Self review is disabled unless enabled in the step.
CheckA JavaScript check that returns an outcome, updates fields, or fails with an error.
ScriptA JavaScript automation, such as an integration with another system.
StatusChanges the target part revision’s lifecycle status. Choose the status in Step details.
ForkBranches into parallel paths. Multiple matching paths from other step types also run in parallel.
JoinWaits for all incoming sources to finish, then proceeds only when every incoming path matches. Otherwise it is skipped. Use it to reunite parallel branches.
EndFinishes a branch. At least one End is required.

Step IDs appear on the canvas and in Step details. Use these IDs when specifying where fields are required. Deleting a step also removes its connected paths.

Keyboard: Tab to focus a step, Enter to edit its details, and arrow keys to move it by 10 pixels. Escape or Cancel connection exits connection mode. Back to start scrolls the canvas to its upper left corner.

Arrange top down lays out the graph in rows from Start to End. Parallel branches share a row. Drag steps to refine the layout; all connections use horizontal and vertical segments and route around other steps. The canvas grows with the diagram. Scroll the workflow tab to navigate; the palette and properties remain beside the diagram on larger screens.

Connections and outcomes

Paths point from a source step’s OUT connector on the bottom to a destination’s IN connector on the top. Drag OUT to IN and release; a dashed preview follows your pointer and a valid destination is highlighted. You can also click an output connector, then IN. Start has no incoming connection; End finishes a branch and has no outgoing connection. The connection banner shows when you are choosing a destination. Click a path line or outcome label to select it and edit its outcome in the designer’s Path details panel. Choose always, success or reject from the suggestions, or type a custom outcome. To remove a path, select its line and click Delete path, or press Delete or Backspace while the canvas is focused.

  • always follows any completed outcome, including rejection.
  • success follows successful completion or approval.
  • reject follows rejection.
  • A script can return a custom outcome name; use that exact name on the path.

All matching paths are followed. An always path and a reject path can both run after a rejection. For mutually exclusive branches, use explicit outcomes. A Join needs all incoming paths to match; do not join alternative approval and rejection branches.

The graph must have no cycles, all steps must be reachable from Start, and End steps cannot have outgoing paths. Save validates the definition and reports invalid settings.

Decision diamonds select exactly one outgoing path. Give each path a unique name such as yes and no; do not use always on a decision. Each named choice has its own output connector on the diamond. Drag that connector to a destination to connect or rewire its branch. Use Add output in Step details for extra choices; connect every output before saving. Human participants see these names as buttons. Programmatic decisions return the same name in outcome. Forms and reviews retain their Complete/Approve and Reject choices.

Form fields and permissions

Each field has a unique Key used in scripts and a Label shown to people. Types are text, textarea, number, boolean or choice. Choice options are comma-separated values.

Required at accepts comma-separated step IDs or start. For example, start, request requires a value when starting and when completing the request step. Leave empty for an optional field.

Can read and Can edit accept comma-separated user:username, group:name, initiator, assignee or *. Here, initiator means the person who started the process; assignee means a person assigned to the current task; * allows everyone. Empty grants no permission in that list. Administrators can read and edit fields regardless of these lists. A field required from a person should be visible and editable to them.

Automated checks and scripts

Define function step(input). The input includes fields, partId, revisionId and idempotencyKey. Return an object with an outcome and optional field updates:

function step(input) {
  return { outcome: "success", fields: { checked: true } };
}

Return false for rejection, or throw an error to fail the step. The editor includes model-check, ERP-order and vendor-PDF examples. Configure endpoints and authentication before using integration examples. Script editing depends on the server’s script-editor settings.

Scripts execute with trusted server capabilities, including plm, http.request, fs and process. Use the supplied idempotency key for external operations that might be retried.

Save and run

If the canvas is empty, add exactly one Start, at least one End, and connect the steps before saving. Save errors appear beside the editor toolbar; your draft stays available while you correct them. Save creates a version of the workflow. Existing processes keep the definition version they started with. Unsaved changes stay in this browser session’s editor draft; save before leaving or reloading the app.

From a part page, select Start workflow to choose an available workflow for the selected revision. The part and revision are filled in automatically. The Revisions tab also offers Start workflow for each revision. To release a part, use a workflow with a Status step set to Released. From Workflows, select Start, enter a process title, choose an optional part and revision, and complete required starting fields. Participants receive Inbox tasks. The process view shows step states, form values and history. Administrators can retry a failed step after fixing its cause. Administrators and the initiator can cancel an active or blocked process.
